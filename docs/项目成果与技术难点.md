# 项目成果与技术难点说明

> 本项目为个人技术演示作品，使用虚构示例数据，不涉及真实单位应用。

## 一、项目成果

### 1. 一个真实可运行的系统
Flask + SQLite 实现的园务设备管理系统，具备完整 CRUD、状态机流转、实时统计看板与 Excel 报表导出。20 个 pytest 用例全部通过，并经浏览器实操验证（截图留证）。

### 2. 一套办公自动化交付物
以系统数据为单一数据源，产出四个办公文件：
- 《园务设备管理系统.xlsx》：5 表工作簿，204 个公式经 LibreOffice 重算零错误，含数据验证、条件格式、真实数据透视表与 4 张原生图表
- 《月度信息工作报告》：正式排版的月度报告（封面 + 三线表 + 分析结论）
- 《信息设备使用与维护培训》：12 页中文培训课件，图表原生可编辑
- 《Excel 数据录入规范》：制度文档，与系统的服务端校验规则逐条对应

### 3. 一套可复现的工程结构
目录分层清晰（app / tests / docs / deliverables / scripts / screenshots），README 提供安装、运行、测试全流程说明；`scripts/` 中的生成脚本可独立复现全部办公文件，改数据即可再生成。

## 二、技术难点与解决过程

### 难点 1：Excel 报表必须"活的"，而不是静态值
**问题**：多数系统导出的 Excel 只是一堆数值，无法满足行政场景"打开还能改、公式可审计"的习惯。
**方案**：导出引擎写入 COUNTIFS/SUMIFS 活公式，月份区间用 `">="&DATE(2026,6,1)` 拼接；所有除法用 IFERROR 包裹避免 #DIV/0!；用 DataValidation 与条件格式把《录入规范》落到文件本身。
**验证**：用 LibreOffice 无头模式重算，204 个公式零错误——为此解决了 LibreOffice Basic 宏在 Windows 上的配置路径问题（`~/.config` 与 `%APPDATA%` 差异导致宏失效、进程挂起）。

### 难点 2：设备与维修单的状态一致性
**问题**：报修后设备仍是"在用"、修完后仍是"维修中"，是台账失真的主要来源。
**方案**：把状态联动做成显式状态机——报修登记自动把在用设备置为维修中；维修单标记已完成时，仅当设备当前状态为"维修中"才恢复"在用"（不覆盖人工设置的其他状态）；含未完结维修单的设备禁止删除。
**验证**：test_create_repair_auto_order_no_and_status_sync、test_update_to_done_restores_device_status 等用例覆盖正反路径。

### 难点 3：报修单号并发安全与可读性
**问题**：单号既要人可读（WX-2610-05，一眼看出年月与顺序），又要防止跳号重号。
**方案**：`next_order_no()` 以 `WX-YYMM-` 前缀查询当月最大序号 +1；SQLite 单写入者的特性使该"查询后插入"模式在演示场景下安全（生产化可升级为 `SELECT ... FOR UPDATE` 或序列表）。

### 难点 4：测试如何不依赖浏览器
**问题**：表单校验、状态机、Excel 内容都要回归，手工点页面不可持续。
**方案**：pytest + Flask test client 覆盖路由与业务规则；Excel 导出用 openpyxl 回读断言工作表结构与首行数据。测试套件首轮就抓出 4 个真实缺陷（SQL 语法错、占位符错位、Row 索引方式错、openpyxl StyleProxy 赋值错），修复后全绿——测试的价值在提交前就兑现了。

### 难点 5：多文档视觉与数据口径统一
**问题**：Excel、Word、PPT、Web 四种载体容易出现"各说各话"的数字。
**方案**：所有交付物共用同一份种子数据与同源配色（深青 #15857A + 橙 #FF6A3B）；Web 端枚举词表、校验规则与《录入规范》条文一一对应；月度报告数字直接取自 LibreOffice 重算后的 Excel 缓存值。
